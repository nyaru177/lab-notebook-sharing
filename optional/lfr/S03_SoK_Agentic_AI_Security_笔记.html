摘要 / Abstract

ENAI agents that combine large language models with non-AI system components are rapidly emerging in real-world applications, offering unprecedented automation and flexibility. However, this unprecedented flexibility introduces complex security challenges that differ from those found in traditional software systems. This paper presents the first comprehensive systematization of knowledge on AI agent security, including an analysis of agents’ design space, attack landscape, and defense mechanisms for secure AI agent systems. We further identify open challenges that point to promising directions for future research in this emerging domain. Our work introduces the first systematic framework for understanding the security risks and defense landscapes of AI agents, serving as a foundation for building both secure agentic systems and advancing research in this critical area.

中将大语言模型与非人工智能系统组件相结合的AI 智能体正在现实世界的应用中迅速兴起，提供前所未有的自动化和灵活性。然而，这种前所未有的灵活性带来了与传统软件系统不同的复杂安全挑战。本文首次全面系统化了AI 智能体安全的知识，包括对安全的 AI 智能体系统的智能体设计空间、攻击版图和防御机制的分析。我们进一步确定了开放的挑战，这些挑战为这一新兴领域的未来研究指明了有希望的方向。我们的工作介绍了第一个用于了解AI 智能体的安全风险和防御版图的系统框架，为构建安全智能体系统和推进这一关键领域的研究奠定了基础。

【补充笔记】SoK 的目标不是提出一个新攻击，而是统一已有概念、建立风险与防御分类，并指出系统性缺口。本文应被当作 Agent 安全架构与综述写作的分类骨架。

1 引言 / Introduction

ENThe rapid advancement of agentic AI systems 1 has fundamentally transformed the AI landscape, marking a paradigm shift from isolated language models to integrated systems that combine Large Language Models (LLMs) with diverse software components. These hybrid systems demonstrate unprecedented capabilities by seamlessly integrating AI models and traditional symbolic software, enabling autonomous task execution and dynamic tool usage. Agentic AI systems span various applications, from software development [28, 44] to web browser use [99, 108]. The security implications of agentic AI systems are becoming increasingly critical as recent incidents demonstrate the severity of potential vulnerabilities. Prompt injection attacks have been exploited to access private GitHub repositories [54], while remote code execution vulnerabilities [88] have enabled unauthorized system access.

中智能体 AI 系统 1 的快速发展从根本上改变了 AI 格局，标志着从孤立的语言模型到将大语言模型 (LLM) 与各种软件组件相结合的集成系统的范式转变。这些混合系统通过无缝集成人工智能模型和传统符号软件，实现了自主任务执行和动态工具使用，展示了前所未有的功能。智能体 AI 系统涵盖各种应用，从软件开发 [28, 44] 到网络浏览器使用 [99, 108]。由于最近发生的事件表明了潜在漏洞的严重性，智能体 AI 系统的安全影响变得越来越重要。提示注入攻击已被利用来访问私有 GitHub 仓库 [54]，而远程代码执行漏洞 [88] 已启用未经授权的系统访问。

ENData exfiltration attacks [112, 117] have compromised sensitive information through malicious document attachments and email forwarding, servers have exposed user chat and credential data [98, 115], and attackers can gain access to users’ personal banking accounts exploiting web agents [13]. These incidents underscore that the flexibility and automation capabilities make agentic systems powerful, while also creating complex security challenges, fundamentally different from traditional software systems or standalone AI models. Existing literature reviews primarily focus on LLM security [49, 58, 81, 138], and the few recent surveys on agents largely concentrate on specific attack vectors or isolated system components [52, 138, 155]. The community lacks a systematic view or framework for understanding the overall risks of the agentic system as a whole, as well as guidance for security principles and mechanisms for agentic systems.

中数据泄露攻击 [112, 117] 通过恶意文档附件和电子邮件转发破坏了敏感信息，服务器暴露了用户聊天和凭证数据 [98, 115]，攻击者可以利用 Web 智能体获取对用户个人银行账户的访问权限 [13]。这些事件强调，灵活性和自动化功能使智能体系统变得强大，同时也带来了复杂的安全挑战，与传统软件系统或独立的人工智能模型根本不同。现有的文献综述主要关注 LLM 安全 [49,58,81,138]，最近对智能体的少数调查主要集中在特定的攻击向量或孤立的系统组件上 [52,138,155]。社区缺乏一个系统的观点或框架来理解整个智能体系统的整体风险，以及智能体系统的安全原则和机制的指导。

ENThis paper addresses this gap by providing the first comprehensive systematization of knowledge on the security landscape of agentic AI systems. We approach agent security from a holistic systems perspective, examining how the combination of LLMs with traditional software creates unique security challenges that cannot be addressed through component-level defenses alone. Our analysis begins with a systematic characterization of agent design dimensions that influence security properties, followed by a comprehensive taxonomy of attack vectors and security risks across the entire agent ecosystem. We then discuss the defense principles for agents and conduct a systematic survey of existing defense mechanisms, categorizing them by their protection approaches. Through the process, we identify limitations in current defenses and discuss open challenges for constructing secure agentic systems.

中本文通过提供有关智能体 AI 系统安全景观的第一个全面的系统化知识来解决这一差距。我们从整体系统的角度来处理智能体安全问题，研究LLM与传统软件的结合如何带来独特的安全挑战，而这些挑战无法仅通过组件级防御来解决。我们的分析首先对影响安全属性的智能体设计维度进行系统表征，然后对整个智能体生态系统的攻击向量和安全风险进行全面分类。然后，我们讨论智能体的防御原则，并对现有防御机制进行系统调查，并按保护方法对它们进行分类。通过这个过程，我们确定了当前防御的局限性，并讨论了构建安全智能体系统的开放挑战。

2 研究概览 / Overview

ENIn this section, we define the scope of our work, introduce our methodology, and discuss the key differences from existing agent security surveys. Scope. We focus on security risks and defenses that are unique to, or significantly amplified in, agentic systems compared to traditional software and standalone LLMs. We first characterize how agents differ from standalone models across seven design dimensions (§3). We then analyze agent-specific security risks both at the component and system levels (§4). For risks that exist in non-agentic LLMs (e.g., jailbreak, hallucination), we emphasize how agent autonomy and environment access magnify their impact (e.g., data exfiltration, unintended system manipulation). We exclude attacks targeting model internals, such as model inversion [38], as these do not fundamentally worsen in agentic contexts where agents operate purely through inference-time input-output interfaces.

中在本节中，我们定义我们的工作范围，介绍我们的方法，并讨论与现有智能体安全调查的主要区别。范围。与传统软件和独立LLM相比，我们专注于智能体系统特有或显著放大的安全风险和防御。我们首先描述智能体与独立模型在七个设计维度上的不同之处（§3）。然后，我们在组件和系统级别分析特定于智能体的安全风险（§4）。对于非智能体LLM中存在的风险（例如，越狱、幻觉），我们强调智能体自治和环境访问如何放大其影响（例如，数据泄露、意外的系统操纵）。我们排除了针对模型内部的攻击，例如模型反转[38]，因为在智能体纯粹通过推理时间输入输出接口进行操作的智能体上下文中，这些攻击不会从根本上恶化。

ENFinally, §5 systematizes the agent defense landscape, describing existing approaches and open challenges. Methodology. First, we define the agent structure and design dimensions based on existing definitions and real-world agent implementations. This forms the foundation of our agent risk taxonomy, which analyzes risks at both the component and system levels. We also refer to the taxonomy of the OW ASP Top 10 for LLM Applications [104] and MITRE ATLAS Matrix [25]. We then propose the defense landscape for agentic systems by applying the defense in-depth principle, informed by traditional system security.

中最后，§5 系统化了智能体防御版图，描述了现有的方法和开放的挑战。方法论。首先，我们根据现有定义和现实世界的智能体实现来定义智能体结构和设计维度。这构成了我们的智能体风险分类法的基础，该分类法分析组件和系统级别的风险。我们还参考了 LLM 申请的 OW ASP Top 10 的分类法 [104] 和 MITRE ATLAS 矩阵 [25]。然后，我们根据传统系统安全性，应用纵深防御，提出智能体系统的防御版图。

ENUnder this framework, we conduct a systematic review of academic literature and web documents on agentic AI security from 2023 to October 2025, corresponding to the proliferation of agent systems [150]. We search with keywords across four dimensions: i) general terminology (e.g., agent security), ii) OW ASP-defined risks (e.g., prompt injection, memory poisoning), iii) component-centric terms (e.g., RAG security, tool security), and iv) traditional security adaptations (e.g., isolation, access control). We prioritize top-tier security venues (e.g., USENIX Security, IEEE S&P, CCS, and NDSS) and ML conferences (e.g., NeurIPS, ICLR, and ICML), alongside high-impact preprints, industry whitepapers, and CVEs. We manually exclude work on standalone models to focus explicitly on agents.

中在此框架下，我们对2023年至2025年10月智能体 AI安全的学术文献和网络文档进行了系统回顾，对应于智能体系统的激增[150]。我们使用四个维度的关键词进行搜索：i) 一般术语（例如，智能体安全），ii) OW ASP 定义的风险（例如，提示注入、记忆投毒），iii) 以组件为中心的术语（例如，RAG 安全、工具安全），以及 iv) 传统安全适应（例如，隔离、访问控制）。我们优先考虑顶级安全场所（例如 USENIX Security、IEEE S&P、CCS 和 NDSS）和 ML 会议（例如 NeurIPS、ICLR 和 ICML），以及高影响力的预印本、行业白皮书和 CVE。我们手动排除独立模型上的工作，以明确关注智能体。

ENThe review yields 128 papers, including 51 attack methods and 60 defense methods; the remaining works address both attacks and defenses or focus on case studies without introducing new methods. Differences From Existing Surveys. Existing surveys on AI and LLM security primarily emphasize model-level threats and overlook the expanded attack surface and downstream consequences introduced by agentic systems [49, 58, 81, 138]. Prior agent-focused studies typically narrow their scope to specific attack vectors [155], agent types [65, 73], or individual components [52], while design-oriented work proposes high-level principles without systematizing attacks or defenses [12, 156]. The closest surveys [31, 151] consider crosscomponent interactions but largely limit their defense taxonomies to model-based techniques.

中评审共 128 篇论文，其中攻击方法 51 种，防御方法 60 种；其余的工作涉及攻击和防御，或者侧重于案例研究，而不引入新方法。与现有调查的差异。现有的人工智能和LLM安全调查主要强调模型级威胁，而忽视了智能体系统带来的扩大的攻击面和下游后果[49,58,81,138]。先前以智能体为中心的研究通常将其范围缩小到特定的攻击向量[155]、智能体类型[65, 73]或单个组件[52]，而面向设计的工作提出了高级原则，但没有系统化攻击或防御[12, 156]。最接近的调查 [31, 151] 考虑了跨组件交互，但很大程度上将其防御分类限制为基于模型的技术。

ENIn contrast, our work provides a unified risk taxonomy covering all agent components and their interactions, together with a defense-in-depth framework that integrates both model-based and system-level defenses, offering actionable guidance for securing agentic systems.

中相比之下，我们的工作提供了涵盖所有智能体组件及其交互的统一风险分类法，以及集成基于模型和系统级防御的纵深防御框架，为保护智能体系统提供了可行的指导。

3.1 AI 智能体 / AI Agents

ENIn this paper, we define AI agents as hybrid software systems that combine traditional software components with neural components.2 An AI agent typically consists of the following components. LLMs. As the brain of the agent, the LLM(s) receive and analyze user tasks, create a step-by-step plan, and take actions following the plan. These processes can be performed by a single or multiple LLMs, each tailored to a specific role. Memory. Memory stores the agent’s internal knowledge base and historical action trajectories, which may include the agent’s past experiences and observations. This information is often vectorized for efficient retrieval and can facilitate the agent to make future decisions based on knowledge and prior experience. Tools. Tools are symbolic functions that the agent uses to interact with the external environment. With tools, agents can perform three types of actions: read, write, and execute.

中在本文中，我们将 AI 智能体定义为将传统软件组件与神经组件相结合的混合软件系统。2 AI 智能体通常由以下组件组成。LLM。作为智能体的大脑，LLM接收并分析用户任务，创建分步计划，并按照计划采取行动。这些流程可以由单个或多个LLM执行，每个LLM都针对特定角色进行定制。记忆。内存存储智能体的内部知识库和历史行动轨迹，其中可能包括智能体过去的经验和观察。这些信息通常被向量化以便有效检索，并且可以帮助智能体根据知识和先前的经验做出未来的决策。工具。工具是智能体用来与外部环境交互的符号功能。通过工具，智能体可以执行三种类型的操作：读取、写入和执行。

ENRetrieval tools provide read-only access to the external environment, such as searching or reading a file, while tools that modify the environment, such as writing a file, sending an email, or running a command, have read, write, and execution access. Tools can be implemented through standardized protocols (e.g., MCP [6]), by the agent designer or by third-party providers [8, 105]. External Environment. External environment is the external context in which the agent interacts to accomplish tasks. Different agents operate in different environments. For example, a web agent typically interacts with a browser, while a code agent operates within an integrated development environment (IDE).

中检索工具提供对外部环境的只读访问权限，例如搜索或读取文件，而修改环境的工具（例如写入文件、发送电子邮件或运行命令）则具有读取、写入和执行访问权限。工具可以由智能体设计者或第三方提供商通过标准化协议（例如 MCP [6]）来实现 [8, 105]。外部环境。外部环境是智能体交互完成任务的外部上下文。不同的智能体在不同的环境中运行。例如，Web 智能体通常与浏览器交互，而代码智能体在集成开发环境 (IDE) 中运行。

ENThe agent interacts with the environment (e.g., access, read, and write to a SQL database) through tools. Overall Workflow. An AI agent receives a user query and automatically takes a sequence of actions to assist the user. The LLM components conduct task planning and decide what actions to take for different tasks, including tool call, content generation, and querying memory. Together, the LLM and the agent workflow form the decision-making core that orchestrates how the agent reasons about tasks and sequences its actions. For example, when asked to update a file, the agent will first call a file read tool, generate new file content based on what it reads, and call a file write tool to update the file.

中智能体通过工具与环境交互（例如，访问、读取和写入 SQL 数据库）。整体工作流程。AI 智能体接收用户查询并自动采取一系列操作来帮助用户。LLM 组件进行任务规划并决定对不同任务采取哪些操作，包括工具调用、内容生成和查询内存。LLM 和智能体工作流程共同构成决策核心，协调智能体如何推理任务并排序其操作。例如，当要求更新文件时，智能体将首先调用文件读取工具，根据读取的内容生成新的文件内容，然后调用文件写入工具来更新文件。

ENAgentic Systems vs. Traditional Software Systems. The key uniqueness of agentic systems compared to traditional systems arises in the composition and workflow of the system. First, agent systems combine traditional software programs with AI models, whereas traditional systems operate mainly on pre-determined program logic defined in source code. This makes agentic systems more flexible and adaptive. Second, workflow in traditional software is mainly pre-programmed, whereas agentic systems run on dynamically generated workflows.

中智能体系统 vs 智能体系统传统软件系统。与传统系统相比，智能体系统的关键独特之处在于系统的组成和工作流程。首先，智能体系统将传统软件程序与人工智能模型相结合，而传统系统主要根据源代码中定义的预先确定的程序逻辑进行操作。这使得智能体系统更加灵活和适应性更强。其次，传统软件中的工作流程主要是预先编程的，而智能体系统则运行在动态生成的工作流程上。

3.2 智能体设计维度 / Agent Design Dimensions

ENWe identify seven design dimensions that characterize agent design. Each dimension represents a continuum spectrum of flexibility, and we illustrate three representative levels (least, moderately, and most flexible) for simplicity. As shown in Table 1, agents can operate at any point along these spectrums. Input Trust. This dimension categorizes the trustworthiness of external data sources on which an agent is relying. It captures the progression from using no external data (highest trust) to relying on arbitrary, potentially untrusted external data sources (lowest trust but highest flexibility). As agents access more diverse and potentially untrusted information sources, they gain improved knowledge and decision-making capabilities, but face increased security risks from compromised or malicious data sources.

中我们确定了代表智能体设计特征的七个设计维度。每个维度都代表灵活性的连续谱，为了简单起见，我们说明了三个代表性级别（最低、中等和最灵活）。如表 1 所示，智能体可以在这些范围内的任何点进行操作。输入信任。该维度对智能体所依赖的外部数据源的可信度进行分类。它捕获了从不使用外部数据（最高信任）到依赖任意、可能不受信任的外部数据源（最低信任但最高灵活性）的进展。随着智能体访问更加多样化且可能不受信任的信息源，他们获得了更高的知识和决策能力，但面临着来自受损或恶意数据源的更大安全风险。

ENAccess Sensitivity. This dimension categorizes an agent’s level of access to sensitive data within the system or environment. Flexibility increases as agents gain access from no sensitive data to known sensitive data sources, and finally to arbitrary sensitive data. Higher levels enable agents to handle more complex tasks that require sensitive information access while significantly expanding both their operational scope and the potential impact of security breaches.

中访问灵敏度。此维度对智能体对系统或环境中敏感数据的访问级别进行分类。随着智能体从无敏感数据访问已知敏感数据源，并最终访问任意敏感数据，灵活性随之增加。更高的级别使智能体能够处理需要敏感信息访问的更复杂的任务，同时显著扩大其操作范围和安全漏洞的潜在影响。

ENWorkflow. This dimension refers to the action sequences of the agent and determines who defines these sequences, analogous to the code in traditional software. Flexibility increases as it shifts from no complex workflows (simple chatbots) to developer-defined workflows, and ultimately to LLM-defined dynamic workflows. This progression allows agents to adapt their execution patterns from rigid, predetermined sequences to flexible, context-aware task planning.

中工作流程。该维度指的是智能体的动作序列，并决定由谁定义这些序列，类似于传统软件中的代码。随着它从无复杂的工作流程（简单的聊天机器人）转变为开发人员定义的工作流程，并最终转变为LLM定义的动态工作流程，灵活性不断提高。这种进展允许智能体将其执行模式从严格的、预定的序列调整为灵活的、上下文感知的任务规划。

ENAction. This dimension specifies the types of operations an agent can perform, with flexibility increasing from generating responses only to adding retrieval capabilities, and finally to executing environment-modifying actions. This progression significantly expands an agent’s operational impact and ability to accomplish complex tasks. This dimension is closely related to the tool dimension, as execution capabilities often require corresponding tools.

中行动。该维度指定智能体可以执行的操作类型，灵活性从仅生成响应到添加检索功能，最后到执行环境修改操作。这一进展显著扩大了智能体的运营影响力和完成复杂任务的能力。这个维度与工具维度密切相关，因为执行能力往往需要相应的工具。

ENTool. This dimension categorizes the range of tools available to an agent, increasing the flexibility from no tools to known, vetted tools, and ultimately to arbitrary tools that can be dynamically discovered and used. This progression maximizes functional capability by expanding the agent’s ability to interact with diverse systems and environments. The tool dimension directly enables the action dimension, as more sophisticated actions typically require more diverse tools.

中工具。此维度对智能体可用的工具范围进行了分类，从而提高了灵活性，从没有工具到已知的、经过审查的工具，并最终到可以动态发现和使用的任意工具。这一进展通过扩展智能体与不同系统和环境交互的能力来最大化功能能力。工具维度直接支持操作维度，因为更复杂的操作通常需要更多样化的工具。

ENMemory. This dimension categorizes how an agent stores and retrieves information, with increasing flexibility from stateless operation to transient session memory and finally to persistent cross-session memory. This progression enables increasingly sophisticated learning, personalization, and knowledge accumulation capabilities. User Interface. This dimension defines how users interact with the agent, increasing flexibility from text-only interaction to web-based previews and media rendering, and ultimately to fully interactive web elements and dynamic interfaces. This progression enables richer user experiences and more complex interaction patterns.

中记忆。此维度对智能体如何存储和检索信息进行分类，从无状态操作到瞬态会话内存，最后到持久的跨会话内存，灵活性不断提高。这种进步使得学习、个性化和知识积累能力变得越来越复杂。用户界面。此维度定义了用户如何与智能体交互，从而提高了从纯文本交互到基于 Web 的预览和媒体渲染，并最终到完全交互式 Web 元素和动态界面的灵活性。这一进展实现了更丰富的用户体验和更复杂的交互模式。

4.1 威胁模型与攻击向量 / Threat Model and Attack Vectors

ENGiven the diverse participants in AI agent ecosystems, attackers and victims vary across different scenarios. We identify three adversary types categorized by the attacker’s capabilities and their corresponding attack vectors. External Adversary. An attacker in the external environment cannot directly interact with the agent, but the attacker can manipulate external resources that the agent may retrieve and process, such as public web pages or documents. This threat model represents the most constrained, yet highly realistic scenario, in which the adversary has no direct access to the agent system.

中鉴于AI 智能体生态系统的参与者多种多样，攻击者和受害者在不同的场景中也有所不同。我们根据攻击者的能力及其相应的攻击向量来识别三种对手类型。外部对手。外部环境中的攻击者无法直接与智能体交互，但攻击者可以操纵智能体可能检索和处理的外部资源，例如公共网页或文档。这种威胁模型代表了最受限制但又高度现实的场景，其中对手无法直接访问智能体系统。

4.2 安全风险 / Security Risks

ENWe present a comprehensive taxonomy of security risks in agents, categorized by components that can be targeted by different attack vectors. This taxonomy provides a systematic map of the entire security risk landscape for agentic systems. We further connect this taxonomy to MITRE ATLAS [25] in Appendix A. R1. Heterogeneous Untrusted Interfaces.Compared to standalone LLMs, agentic systems expose multiple heterogeneous interfaces to users, including external data sources that agents retrieve and process, persistent memory stores that accumulate over time, and third-party tools with various trust levels. These interfaces can be leveraged by attackers as attack entry points, which introduce way larger attack surfaces compared to standalone LLMs. R2. Wrong Instruction Following.

中我们提出了智能体安全风险的全面分类法，按不同攻击媒介的目标组件进行分类。该分类法提供了智能体系统整个安全风险格局的系统图。我们进一步将该分类法与附录 A.R1 中的 MITRE ATLAS [25] 连接起来。异构不可信接口。与独立的LLM相比，智能体系统向用户公开多个异构接口，包括智能体检索和处理的外部数据源、随着时间累积的持久内存存储以及具有不同信任级别的第三方工具。攻击者可以利用这些接口作为攻击入口点，与独立的 LLM 相比，这会引入更大的攻击面。 R2。遵循错误的指令。

ENThe agent follows malicious prompts injected by attackers rather than the intended instructions from benign users or system developers. This occurs because inputs from external or attacker-controlled sources are processed by the model inside the agent and can therefore influence its behavior. R3. Unconstrained/Unsafe Data Flow. LLMs suffer from unconstrained data flow due to their stochastic nature. In agentic systems, this manifests as data flowing freely from any input from untrusted interfaces (R1) to any output (e.g., user responses or subsequent tool calls), unlike traditional systems where data propagation is regulated by programming languages, type systems, and access controls. This leads to consequential risks: private data leakage (R5), data corruption (R6), and resource drain (R7). For example, when an agent retrieves untrusted web content and produces a URL in its response, that URL may contain attacker-controlled data.

中该智能体遵循攻击者注入的恶意提示，而不是良性用户或系统开发人员的预期指令。发生这种情况是因为来自外部或攻击者控制源的输入由智能体内部的模型处理，因此可以影响其行为。R3。不受约束/不安全的数据流。由于其随机性，LLM面临着不受约束的数据流。在智能体系统中，这表现为数据从不受信任的接口（R1）的任何输入自由流向任何输出（例如，用户响应或后续工具调用），这与数据传播由编程语言、类型系统和访问控制控制的传统系统不同。这会导致随之而来的风险：私有数据泄漏（R5）、数据损坏（R6）和资源耗尽（R7）。例如，当智能体检索不受信任的 Web 内容并在其响应中生成 URL 时，该 URL 可能包含攻击者控制的数据。

ENAutomatically fetching such URLs enables data exfiltration [87, 112], resulting in R5. R4. Hallucination and Model Mistakes. Models often hallucinate and generate incorrect information, and this problem becomes more severe in agent-environment interactions because agents act on hallucinated content, creating real-world consequences beyond misinformation, such as accessing attackercontrolled resources. Attackers exploit this behavior through package hallucination attacks [127], where they register malicious packages with names that LLMs frequently hallucinate. This turns a model limitation into a reliable attack vector for code injection and supply chain compromise.

中自动获取此类 URL 会导致数据泄露 [87, 112]，从而导致 R5。R4。幻觉和模型错误。模型经常产生幻觉并生成不正确的信息，并且这个问题在智能体与环境交互中变得更加严重，因为智能体对幻觉内容进行操作，除了错误信息之外还会产生现实世界的后果，例如访问攻击者控制的资源。攻击者通过包幻觉攻击来利用这种行为[127]，他们使用LLM经常幻觉的名称注册恶意包。这将模型限制变成了代码注入和供应链妥协的可靠攻击向量。

ENR5. Private Data Leakage. Agents handle sensitive data across multiple components such as user conversations, persistent memory, tool credentials, and environment resources, creating opportunities for unauthorized data access. Attackers exploit interactions among these components to exfiltrate private information. Examples include manipulating agents to send data to attacker-controlled servers, triggering automatic URL fetches that leak data through request parameters, or abusing domain-specific vulnerabilities such as SSRF, XSS, path traversal, or SQL injection to reach protected resources. Recent incidents [90, 98, 115] show real confidentiality violations where agent vulnerabilities exposed users’ chat histories and personal information.

中R5。私人数据泄露。智能体跨多个组件处理敏感数据，例如用户对话、持久内存、工具凭证和环境资源，从而为未经授权的数据访问创造了机会。攻击者利用这些组件之间的交互来窃取私人信息。示例包括操纵智能体将数据发送到攻击者控制的服务器、触发通过请求参数泄漏数据的自动 URL 获取，或者滥用特定于域的漏洞（例如 SSRF、XSS、路径遍历或 SQL 注入）来访问受保护的资源。最近的事件 [90,98,115] 显示了真正的机密违规行为，其中智能体漏洞暴露了用户的聊天历史和个人信息。

ENR6. Unintended/Unauthorized Action and Data Corruption. Agents can violate integrity through two closely related risks, unintended and unauthorized actions and data corruption, both involving unauthorized changes to internal or external state. Unintended actions make irreversible state changes (e.g., unauthorized purchases, arbitrary code execution), while data corruption directly modifies stored resources (e.g., corrupting files or databases). At the user interface, agents may provide false or misleading information. At memory components, agents may inject poisoned knowledge or malicious instructions [21] that corrupt subsequent behavior.

中R6。意外/未经授权的行为和数据损坏。智能体可能会通过两种密切相关的风险来违反完整性：意外和未经授权的操作以及数据损坏，这两种风险都涉及对内部或外部状态的未经授权的更改。意外操作会导致不可逆的状态更改（例如，未经授权的购买、任意代码执行），而数据损坏会直接修改存储的资源（例如，损坏文件或数据库）。在用户界面上，智能体可能会提供虚假或误导性信息。在内存组件中，智能体可能会注入有毒的知识或恶意指令[21]，从而破坏后续行为。

ENAt the environment level, agents can be manipulated to execute unauthorized modifications through command injection, SQL injection, or file system manipulation. R7. Resource Drain and Denial-of-Service. Agents introduce availability risks through their consumption of computational resources, API calls, and interactions with external systems. Attackers exploit this autonomy to trigger costly API calls, force infinite execution loops, or cause excessive memory use, creating denial-of-service conditions that can render the agent and external systems unusable or economically unsustainable. Other risks in agentic systems. Attackers can also target the agentic AI system itself, rather than the user or surrounding environment, by stealing system prompts, tool descriptions, and configurations that encode proprietary knowledge [120, 148], undermining agent developers and tool providers.

中在环境级别，可以通过命令注入、SQL 注入或文件系统操作来操纵智能体执行未经授权的修改。R7。资源消耗和拒绝服务。智能体通过消耗计算资源、API 调用以及与外部系统的交互引入可用性风险。攻击者利用这种自主性来触发昂贵的 API 调用、强制无限执行循环或导致内存使用过多，从而创建拒绝服务条件，从而导致智能体和外部系统无法使用或在经济上不可持续。智能体系统中的其他风险。攻击者还可以通过窃取系统提示、工具描述和编码专有知识的配置来瞄准智能体 AI 系统本身，而不是用户或周围环境[120, 148]，从而破坏智能体开发人员和工具提供商。

ENAgentic systems may also expose side-channel risks through observable behaviors such as tool execution timing, API call sequences, or network traffic patterns. To the best of our knowledge, we are not aware of prior work studying such side-channel attacks in agentic systems, and thus defer deeper analysis to future work.

中智能体系统还可能通过可观察的行为（例如工具执行时间、API 调用序列或网络流量模式）暴露旁路风险。据我们所知，我们不知道之前有研究智能体系统中此类侧信道攻击的工作，因此将更深入的分析推迟到未来的工作中。

中扩展外部数据源可以实现间接提示注入，添加持久内存会造成记忆投毒目标，而合并第三方工具会带来供应链风险。工作流程维度主要驱动模型风险（R2、R3、R4）。随着工作流程从简单的聊天机器人转向 LLM 定义的动态执行，灵活的控制流为劫持智能体推理、恶化错误指令跟踪和不受约束的数据流提供了更多机会。当智能体动态选择工具和资源时，幻觉风险会放大，因为不正确的模型输出会直接触发现实世界的行动。访问敏感性、操作和用户界面维度确定后果风险的严重程度（R5、R6、R7）。授予智能体访问更敏感数据的权限会放大违规的影响，因为受损的智能体可能会泄漏、损坏或耗尽更有价值的资源。

ENExpanding action capabilities from response-only to execution transforms information disclosure into environment corruption. Complex user interfaces introduce new attack channels through automatic URL fetching (confidentiality), executing destructive commands (integrity), and interface manipulation (availability). Risk Interactions and Amplification. Risks in agentic systems (R1-R7) interact in a cascading manner, where initial failures propagate across components and amplify system-level threats. An expanded attack surface (R1) increases entry points for attacker-controlled data, allowing malicious inputs to reach and exploit model risks (R2, R3, R4). For example, indirect prompt injection through external data can trigger wrong instruction following, which then redirects agent behavior.

中将行动能力从仅响应扩展到执行，将信息泄露转变为环境腐败。复杂的用户界面通过自动 URL 获取（保密性）、执行破坏性命令（完整性）和界面操作（可用性）引入了新的攻击渠道。风险相互作用和放大。智能体系统 (R1-R7) 中的风险以级联方式相互作用，其中初始故障跨组件传播并放大系统级威胁。扩展的攻击面 (R1) 增加了攻击者控制的数据的入口点，允许恶意输入到达并利用模型风险（R2、R3、R4）。例如，通过外部数据间接提示注入可能会触发错误的指令遵循，从而重定向智能体行为。

ENModel risks then amplify consequence risks (R5, R6, R7). Wrong instruction following can lead to data exfiltration (confidentiality), data corruption (integrity), or excessive resource consumption (availability). Unconstrained data flow heightens confidentiality and integrity risks by enabling data leakage and malicious code execution. Hallucination increases integrity risks by causing agents to operate on fabricated resources, leading to data leakage and corruption.

中然后模型风险会放大后果风险（R5、R6、R7）。错误的指令遵循可能导致数据泄露（保密性）、数据损坏（完整性）或过多的资源消耗（可用性）。不受约束的数据流会导致数据泄露和恶意代码执行，从而增加了保密性和完整性风险。幻觉会导致智能体在伪造的资源上进行操作，从而增加完整性风险，从而导致数据泄漏和损坏。

【精读笔记】最值得记住的风险链：R1 攻击面扩大 → R2/R3/R4 模型与控制流失效 → R5/R6/R7 真实安全后果。

【精读笔记】防御应沿攻击链布置：入口检查 → 规划目标检查 → 信息流限制 → 工具权限检查 → 执行后果限制。

5.1 安全目标 / Security Goals

ENIn this section, we discuss the security goals for AI agents. They are based on standard security principles, specifically the Confidentiality, Integrity, and Availability (CIA) triad that forms the foundation of traditional security frameworks. Additionally, we introduce Contextual Security as a new security goal for agentic systems. Confidentiality. Confidentiality ensures that all information is accessible only to authorized entities. It includes protecting system-level secrets (API keys), agent internal memory, user private data, and LLM-related data (model parameters, system prompts).

中在本节中，我们讨论AI 智能体的安全目标。它们基于标准安全原则，特别是构成传统安全框架基础的保密性、完整性和可用性 (CIA) 三元组。此外，我们引入上下文安全作为智能体系统的新安全目标。保密。保密性确保所有信息只有授权实体才能访问。它包括保护系统级机密（API密钥）、智能体内存、用户私有数据和LLM相关数据（模型参数、系统提示）。

ENThis goal addresses unconstrained data flow (R3) and private data leakage (R5). Integrity. Integrity ensures that all data in the agent system and the external environment remain trustworthy and unmodified by unauthorized entities. This includes preventing tampering with agent memory, LLM outputs, tool results, and environment data, as well as ensuring that agents are not manipulated to perform unintended actions through malicious instructions. The security goals associated with integrity can be different for different agents, depending on the components they have, as well as the data and control flows. This goal addresses heterogeneous untrusted interfaces (R1), wrong instruction following (R2), unconstrained data flow (R3), hallucination (R4), and unintended action and data corruption (R6).

中此目标解决不受约束的数据流 (R3) 和私有数据泄漏 (R5)。诚信。完整性确保智能体系统和外部环境中的所有数据保持可信且不会被未经授权的实体修改。这包括防止篡改智能体内存、LLM 输出、工具结果和环境数据，以及确保智能体不会被恶意指令操纵以执行意外操作。对于不同的智能体，与完整性相关的安全目标可能不同，具体取决于它们拥有的组件以及数据和控制流。该目标解决异构不可信接口 (R1)、错误指令遵循 (R2)、不受约束的数据流 (R3)、幻觉 (R4) 以及意外操作和数据损坏 (R6)。

ENAvailability. Availability protects against resource abuse when LLM inference and tools consume user resources. This includes preventing token draining and protecting external systems and agent hosts from denial-of-service attacks. This goal addresses resource drain and denial-of-service (R7). Contextual Security. As discussed in §3, dynamic contexts are unique and essential to an AI agent’s overall functionality and security. Given that agents actively interact with the environment, the retrieved information will eventually be fed to the planning and actor LLMs through their context. Accordingly, recent studies define contextual security [122, 132] as a critical security goal for AI agents. Contextual security ensures that the agent’s contexts are aligned with the agent’s intended user tasks, preventing attacks aimed at manipulating contexts during agent execution. It complements confidentiality and integrity that protect data correctness and secrecy, while contextual security governs which context elements (e.g., system prompts, user goals, tool descriptions, retrieved snippets) are admissible and how they are prioritized to avoid instruction override, context drift, or unsafe tool selection.

中可用性。当 LLM 推理和工具消耗用户资源时，可用性可以防止资源滥用。这包括防止令牌耗尽以及保护外部系统和智能体主机免受拒绝服务攻击。此目标解决资源消耗和拒绝服务 (R7) 问题。上下文安全。正如第 3 节中所讨论的，动态上下文对于 AI 智能体的整体功能和安全性来说是独特且必不可少的。鉴于智能体主动与环境交互，检索到的信息最终将通过其上下文反馈给规划和执行者LLM。因此，最近的研究将上下文安全 [122, 132] 定义为AI 智能体的关键安全目标。上下文安全确保智能体的上下文与智能体的预期用户任务保持一致，从而防止在智能体执行期间针对操纵上下文的攻击。它补充了保护数据正确性和保密性的保密性和完整性，而上下文安全则控制哪些上下文元素（例如，系统提示、用户目标、工具描述、检索到的片段）是可接受的，以及如何确定它们的优先级，以避免指令覆盖、上下文漂移或不安全的工具选择。

【精读笔记】上下文安全检查哪些内容能进入上下文、哪些是指令、谁的优先级更高、工具选择是否仍服务于原始任务，以及是否发生 context drift。

5.2 运行时保护 / Runtime Protection

ENRuntime protection mechanisms provide dynamic security enforcement during agent execution, detecting real-time threats and behaviors.

中运行时保护机制在智能体执行期间提供动态安全实施，检测实时威胁和行为。

【补充笔记】运行时保护要覆盖内容进入、计划形成、工具调用、数据外发和状态写入。单一 Guardrail 只覆盖其中一层，无法替代最小权限、隔离、完全仲裁和持续监控。

5.2.1 输入护栏 / Input Guardrail

ENInput guardrails validate inputs before they reach the agent. They provide a first-line defense by preventing malicious instructions and data from reaching downstream components. By filtering malicious inputs early, input guardrails mitigate heterogeneous untrusted interfaces (R1) risks from untrusted data sources. Input guardrails apply to both standalone models and agents. For standalone models, input guardrails focus on detecting malicious inputs such as jailbreak prompts or harmful content [22, 55, 82, 119, 123]. These techniques remain effective in agentic settings to validate various inputs, especially those from external environments.

中输入护栏在输入到达智能体之前对其进行验证。它们通过防止恶意指令和数据到达下游组件来提供一线防御。通过尽早过滤恶意输入，输入护栏可以减轻来自不可信数据源的异构不可信接口 (R1) 风险。输入护栏适用于独立模型和智能体。对于独立模型，输入护栏专注于检测恶意输入，例如越狱提示或有害内容[22,55,82,119,123]。这些技术在智能体环境中仍然有效，可以验证各种输入，尤其是来自外部环境的输入。

ENSpecifically to agents, input guardrails address risks introduced by dynamic data retrieval and tool execution, verifying the trustworthiness of retrieved data. For instance, agents enforce URL allowlists [46] to constrain data retrieval to trusted sources, mitigating risks from untrusted web content. Representative Works. NeMo Guardrails [110] provides a domain-specific language for developer-defined input filters with customizable validation rules. Constitutional classifiers [119], llama-firewall [22], and PromptShield [55] employ specialized models to detect both direct and indirect prompt injection attempts in user inputs and external data. DataSentinel [82] leverages a prompt injection-vulnerable model to improve detection rates by identifying subtle injection patterns that bypass other guardrails.

中特别是对于智能体来说，输入护栏可以解决动态数据检索和工具执行带来的风险，验证检索数据的可信度。例如，智能体强制执行 URL 白名单 [46]，以将数据检索限制在可信来源，从而减轻来自不可信 Web 内容的风险。代表作品。NeMo Guardrails [110] 为开发人员定义的输入过滤器提供了一种特定于域的语言，并具有可定制的验证规则。宪法分类器 [119]、llama-firewall [22] 和 PromptShield [55] 采用专门的模型来检测用户输入和外部数据中的直接和间接提示注入尝试。DataSentinel [82] 利用即时注入易受攻击的模型，通过识别绕过其他护栏的微妙注入模式来提高检测率。

ENDesign Dimensions. Input guardrail design varies across three dimensions: detection mechanism, validation target, and mitigation strategy. • Detection mechanism: Input guardrails face a fundamental tradeoff between security strictness and operational flexibility. Rule-based detection offers strict protection through predefined patterns [110] or endpoint allowlists [45, 46], whereas model-based detection provides adaptive protection through classifiers [22, 55, 82, 119, 123] that detect malicious patterns in content. • Validation target: Input guardrail validates various aspects of input data. Content-based guardrails [22, 55, 119, 123] examine semantic input for malicious patterns or harmful content, while source-based guardrails [46] verify data origin trustworthiness, uniquely addressing agents’ dynamic retrieval from external sources like web search and databases.

中设计尺寸。输入护栏设计在三个维度上有所不同：检测机制、验证目标和缓解策略。• 检测机制：输入护栏面临安全严格性和操作灵活性之间的根本权衡。基于规则的检测通过预定义模式 [110] 或端点白名单 [45, 46] 提供严格的保护，而基于模型的检测通过检测内容中的恶意模式的分类器 [22, 55, 82, 119, 123] 提供自适应保护。• 验证目标：输入护栏验证输入数据的各个方面。基于内容的护栏[22,55,119,123]检查语义输入是否存在恶意模式或有害内容，而基于源的护栏[46]验证数据源的可信度，独特地解决智能体从网络搜索和数据库等外部源的动态检索。

EN• Mitigation strategy: Guardrails can simply detect and filter out malicious input [22, 55, 82, 119], sanitize malicious portion before incorporating the input into the system [123], or normalize input in a structured format with type system and validation [161] to reduce attack surface. Limitations and Open Challenges. As the input space becomes vast and diverse, it is challenging to establish universal security criteria. Model-based detectors are often bypassed by adaptive attacks [5], and rule-based detectors require extensive human effort and difficult to be generalized. Consequently, input guardrails often suffer from false positives and false negatives, which negatively impact the agent’s utility and security. False positives are caused partly by the limited detection accuracy, but more importantly, by ambiguous definitions and boundaries between secure and insecure data and instructions. False negatives allow attackers to bypass input guardrails and inject malicious inputs into the target agent.

中• 缓解策略：Guardrails 可以简单地检测并过滤掉恶意输入 [22,55,82,119]，在将输入合并到系统之前清理恶意部分 [123]，或者使用类型系统和验证 [161] 以结构化格式规范输入以减少攻击面。局限性和开放挑战。随着输入空间变得广阔和多样化，建立通用的安全标准具有挑战性。基于模型的检测器经常被自适应攻击绕过[5]，而基于规则的检测器需要大量的人力并且难以推广。因此，输入护栏经常会出现误报和误报，这会对智能体的实用性和安全性产生负面影响。误报的部分原因是检测精度有限，但更重要的是，安全与不安全数据和指令之间的定义和界限不明确。漏报允许攻击者绕过输入护栏并将恶意输入注入目标智能体。

【补充笔记】输入护栏面对开放输入空间，容易被自适应攻击绕过，也会产生误报和漏报。正确定位是风险降低组件，而不是安全边界；即使检测失败，后续权限控制仍应阻止严重后果。

5.2.2 输出护栏 / Output Guardrail

ENOutput guardrails perform security checks on an agent’s output behaviors, such as responses to users and tool usages to interact with external systems. They complement input guardrails by preventing attacks that appear seemingly benign but trigger malicious actions [87]. Output guardrails mitigate wrong instruction following(R2) by validating task alignment, hallucination (R4) through output verification, private data leakage (R5) by checking for sensitive data exposure, and unintended actions and data corruption (R6) by validating tool usage. Output guardrails for LLMs typically focus on detecting harmful outputs, using classifiers or programmable rules [85, 89, 110, 119]. Agent-specific output guardrails validate tool usage and action sequences [20,57,84,122,132,146], ensuring context-dependent policies and alignment with the user intent. Representative Works.

中输出护栏对智能体的输出行为执行安全检查，例如对用户的响应以及与外部系统交互的工具使用情况。它们通过防止看似良性但会触发恶意行为的攻击来补充输入护栏[87]。输出护栏通过验证任务对齐来减少错误指令遵循 (R2)，通过输出验证减少幻觉 (R4)，通过检查敏感数据暴露来减少私有数据泄漏 (R5)，通过验证工具使用来减少意外操作和数据损坏 (R6)。LLM的输出护栏通常侧重于使用分类器或可编程规则检测有害输出[85,89,110,119]。特定于智能体的输出护栏验证工具使用和操作序列[20,57,84,122,132,146]，确保上下文相关的策略并与用户意图保持一致。代表作品。

ENProgent [122], Conseca [132], and Agrail [84] generate adaptive security policies based on the runtime context to prevent environment data leakage, corruption, and resource drain through dynamic policy enforcement. GuardAgent [146] and ShieldAgent [20] create domain-specific security checks based on human-provided policies, allowing customized protection for specialized agent applications. CodeShield and HeimdallM [85, 89] apply static analysis techniques to agent-generated code, preventing arbitrary code execution through vulnerability detection. Network allowlists [46] restrict agent network connections to preauthorized domains, preventing data exfiltration through unauthorized web endpoints. Design Dimensions. Output guardrail design varies across two dimensions: detection goal and detection mechanism.

中Progent [122]、Conseca [132] 和 Agrail [84] 基于运行时上下文生成自适应安全策略，通过动态策略实施来防止环境数据泄漏、损坏和资源耗尽。GuardAgent [146] 和 ShieldAgent [20] 根据人工提供的策略创建特定于域的安全检查，从而允许为专用智能体应用程序提供定制保护。CodeShield 和 HeimdallM [85, 89] 将静态分析技术应用于智能体生成的代码，通过漏洞检测防止任意代码执行。网络白名单 [46] 将智能体网络连接限制到预先授权的域，防止数据通过未经授权的 Web 端点泄露。设计尺寸。输出护栏设计在两个维度上有所不同：检测目标和检测机制。

EN• Detection goal: Output guardrails detect harmful content in LLM outputs [110, 119], unsafe code [85, 89], and unsafe actions in tool usage [122, 132]. Further, output guardrails perform alignment checks to ensure agent’s behavior remain within user intent [22, 57], data privacy protection [27], domain-specific policy enforcement [20,84,146], and runtime-aware contextual security enforcement [122, 132]. • Detection mechanism: Mechanisms of output guardrails range from rule-based pattern matching [85, 89] to model-based classifiers [22, 110, 119]. Hybrid approaches adopt a structured policy framework assisted by models to process unstructured data, enabling flexible security enforcement [20, 27, 84, 122, 132, 146]. Limitations and Open Challenges.

中• 检测目标：输出护栏检测LLM 输出中的有害内容[110, 119]、不安全代码[85, 89] 以及工具使用中的不安全操作[122, 132]。此外，输出护栏执行对齐检查，以确保智能体的行为保持在用户意图 [22, 57]、数据隐私保护 [27]、特定于域的策略执行 [20,84,146] 和运行时感知上下文安全执行 [122, 132] 范围内。• 检测机制：输出护栏机制的范围从基于规则的模式匹配[85, 89]到基于模型的分类器[22, 110, 119]。混合方法采用模型辅助的结构化策略框架来处理非结构化数据，从而实现灵活的安全实施[20,27,84,122,132,146]。局限性和开放挑战。

ENOutput guardrails share similar limitations with input guardrails, including false positives and negatives due to unclear security criteria, and a tradeoff between rule-based and model-based solutions. Compared to input guardrails, output guardrails consume more computational resources and time, as they have a dependency on the LLM’s output and need to process more data [138].

中输出护栏与输入护栏具有类似的局限性，包括由于安全标准不明确而导致的误报和误报，以及基于规则和基于模型的解决方案之间的权衡。与输入护栏相比，输出护栏消耗更多的计算资源和时间，因为它们依赖于LLM的输出并且需要处理更多的数据[138]。

【精读笔记】Agent 的输出护栏不能只审核回答，还应检查生成代码、工具选择、工具参数、行动序列和数据外发目标。

5.2.3 信息流控制与污点追踪 / Information Flow Control and Taint Tracking

ENInformation Flow Control (IFC) [32, 92] and taint tracking [95] restrict the flow of information within a system. Classical IFC techniques assign each piece of data a security label from a predefined information flow lattice [32], propagate labels, and detect flows that violate the lattice constraints. IFC and taint tracking in agents address the model’s inherent unconstrained data flow (R3), and further mitigate downstream confidentiality (R5) and integrity (R6) violations. Representative Works. PFI [60], CaMeL [29], and FIDES [26] transform tool results into symbolic variables to deterministically track data flow through agent operations. PFI prevents untrusted external data from controlling tool arguments, while CaMeL and FIDES ensure credential data, such as secret codes, are not leaked to untrusted endpoints like malicious email recipients.

中信息流控制 (IFC) [32, 92] 和污点跟踪 [95] 限制系统内的信息流。经典的 IFC 技术为每条数据分配一个来自预定义信息流网格 [32] 的安全标签，传播标签并检测违反网格约束的流。智能体中的 IFC 和污点跟踪解决了模型固有的无约束数据流 (R3) 问题，并进一步减轻了下游保密性 (R5) 和完整性 (R6) 违规问题。代表作品。PFI [60]、CaMeL [29] 和 FIDES [26] 将工具结果转换为符号变量，以通过智能体操作确定性地跟踪数据流。PFI 可防止不受信任的外部数据控制工具参数，而 CaMeL 和 FIDES 可确保凭证数据（例如密码）不会泄露给不受信任的端点（例如恶意电子邮件收件人）。

ENThese approaches commonly pair with privilege separation techniques to process input data into variables with restricted privileges. Permissive information flow control [124] measures the influence of each LLM input on output by performing an inference multiple times with different input combinations. Melon [160] extends this influence measurement to control and data flows of the agent, by comparing the agent’s tool usage with and without specific inputs, and blocking potentially manipulated tool calls. Design Dimensions. IFC and taint tracking designs vary across security goals and mechanisms, spanning non-agentic LLM outputs and agent tool executions. • Security Goals: Previous works provide integrity and confidentiality protection in agents.

中这些方法通常与权限分离技术结合使用，将输入数据处理为具有受限特权的变量。宽容信息流控制[124]通过使用不同的输入组合多次执行推理来测量每个LLM输入对输出的影响。Melon [160] 通过比较智能体在有或没有特定输入时的工具使用情况，并阻止可能被操纵的工具调用，将这种影响测量扩展到智能体的控制和数据流。设计尺寸。IFC 和污点跟踪设计因安全目标和机制而异，涵盖非智能体 LLM 输出和智能体工具执行。• 安全目标：以前的工作为智能体提供了完整性和保密性保护。

ENIntegrity protection blocks untrusted inputs from influencing tool call decisions [60, 158, 160]. Confidentiality protection prevents sensitive data from reaching untrusted sinks [26, 29, 69, 137]. • Mechanisms: IFC and taint tracking mechanisms include symbolic variable-based, multi-execution-based, and model-based approaches. Multi-execution [124,160] measures the influence of an input on an output by performing the LLM inference multiple times with and without the input. Variable-based approaches replace data with trackable variables to mitigate overtainting while retaining deterministic information flow guarantee [26, 29, 60, 69]. Model-based approach request LLMs to inspect information flow given agent traces [71, 136, 137, 158].

中完整性保护阻止不受信任的输入影响工具调用决策[60,158,160]。机密保护可防止敏感数据到达不受信任的接收器 [26,29,69,137]。• 机制：IFC 和污点跟踪机制包括基于符号变量、基于多重执行和基于模型的方法。多重执行[124,160]通过在有输入和无输入的情况下多次执行LLM推理来测量输入对输出的影响。基于变量的方法用可跟踪变量替换数据，以减轻过度污染，同时保留确定性信息流保证[26,29,60,69]。基于模型的方法要求LLM检查给定智能体跟踪的信息流[71,136,137,158]。

ENLimitations and Open Challenges. Existing IFC and taint methods incur substantial runtime overhead with multiexecution or variable-based reasoning, limiting practicality for latency-sensitive agents. They may also suffer from label creep, where conservative propagation renders agents unusable unless automated and safe declassification rules are devised. Bridging these gaps requires lightweight information flow tracking and principled policies for relaxing security labels when it is safe to do so, without compromising security.

中局限性和开放挑战。现有的 IFC 和污点方法会因多重执行或基于变量的推理而产生大量运行时开销，从而限制了延迟敏感智能体的实用性。它们还可能遭受标签蠕变的影响，除非设计出自动且安全的解密规则，否则保守的传播会使智能体无法使用。弥合这些差距需要轻量级信息流跟踪和原则性策略，以便在安全的情况下放宽安全标签，同时又不影响安全性。

【补充笔记】信息流控制有两个目标：从完整性看，不可信网页不能控制高权限工具；从保密性看，秘密数据不能流向不可信目标。自然语言中的间接影响、标签扩散和推理开销是主要难点。

5.2.4 监控 / Monitoring

ENUnder the dynamic and unpredictable nature of AI agents, monitoring offers system-wide visibility by checking inputs, outputs, and intermediate states. This holistic view helps surface distributed threats where no single input or action appears malicious in isolation but collectively constitutes a malicious goal [140, 152]. Monitoring can be important to observe interactions across tools and services over long runs, especially for multi-agent systems. Monitoring mitigates private data leakage (R5), unintended actions and data corruption (R6), and resource drain and denial of service (R7) by detecting anomalous behaviors across long-running agent executions. Representative Works. Previous work urged the need for monitoring distributed harm, where malicious tasks are broken down into seemingly benign subtasks and bypass guardrails [140, 152].

中在AI 智能体的动态和不可预测的性质下，监控通过检查输入、输出和中间状态来提供系统范围的可见性。这种整体视图有助于揭示分布式威胁，其中没有任何单个输入或操作单独出现恶意，但共同构成恶意目标 [140, 152]。监控对于长期观察工具和服务之间的交互非常重要，特别是对于多智能体系统。监控通过检测长时间运行的智能体执行中的异常行为，减少私有数据泄漏 (R5)、意外操作和数据损坏 (R6) 以及资源消耗和拒绝服务 (R7)。代表作品。之前的工作敦促需要监控分布式危害，其中恶意任务被分解为看似良性的子任务并绕过护栏 [140, 152]。

ENAgentMonitor [93] detects security violations in Web and file access environments by scoring behavioral risks. AgentAuditor [83] constructs feature memory for unsafe agent actions to detect anomalies at run-time. SentinelAgent [51] and Guardian [159] detect anomalies in multi-agent systems through interaction graph modeling. Design Dimensions. Monitoring design varies across detection goals and log granularity. • Detection goals: Monitoring systems target different threat categories, including anomaly detection over long agent trajectories [51,83,93], and interaction-graph monitoring in multi-agent systems [159].

中AgentMonitor [93] 通过对行为风险进行评分来检测 Web 和文件访问环境中的安全违规行为。AgentAuditor [83] 为不安全的智能体操作构建特征内存，以在运行时检测异常。SentinelAgent [51] 和 Guardian [159] 通过交互图建模来检测多智能体系统中的异常情况。设计尺寸。监控设计因检测目标和日志粒度而异。• 检测目标：监控系统针对不同的威胁类别，包括长智能体轨迹的异常检测[51,83,93]，以及多智能体系统中的交互图监控[159]。

EN• Log Granularity: Agent activity log ranges from coarse summaries of actions and tool calls to fine-grained traces that capture intermediate reasoning steps and parameters. Finer granularity improves detection power but increases storage, computation, and privacy exposure [15]. Limitations and Open Challenges. While monitoring techniques provide a holistic view of agent execution, they suffer from fundamental limitations of runtime defenses, such as inaccuracy issues and performance overhead. Agent behaviors are stochastic and context-dependent, making it hard to distinguish benign actions from harmful ones. Static rules miss novel attacks, whereas adaptive models incur overhead and remain susceptible to evasion. Moreover, long-lived executions would further accumulate logs, for which storage overhead and privacy controls remain largely unexplored.

中• 日志粒度：智能体活动日志的范围从操作和工具调用的粗略摘要到捕获中间推理步骤和参数的细粒度跟踪。更细的粒度提高了检测能力，但增加了存储、计算和隐私暴露[15]。局限性和开放挑战。虽然监控技术提供了智能体执行的整体视图，但它们受到运行时防御的基本限制，例如不准确问题和性能开销。智能体行为是随机的且依赖于上下文，因此很难区分良性行为和有害行为。静态规则会错过新的攻击，而自适应模型会产生开销并且仍然容易被规避。此外，长期执行会进一步积累日志，而存储开销和隐私控制在很大程度上仍未被探索。

【补充笔记】监控应观察完整任务轨迹。单步操作可能都合理，但组合后可能形成目标漂移、持续泄露、异常 Agent 通信或资源滥用；因此日志需要同时支持检测、审计和回滚。

5.2.5 人在回路验证 / Human-In-The-Loop Validation

ENTraditional security employs user consent mechanisms for app installation [36] and sensitive data access [9]. In agentic settings, human-in-the-loop validation allows users to validate agent behavior and tool usage, providing user-customized control over security decisions. Human-in-the-loop validation mitigates private data leakage (R5), unintended actions and data corruption (R6), and resource drain and denial of service (R7). This defense is relatively unique to agents, as agents act on behalf of users and interact with external environments (e.g., files, web, third-party tools), requiring user confirmation before high-risk actions. Representative Works. While limited literature has been dedicated to discussing human-in-the-loop validation for agents, contemporary coding agents such as GitHub Copilot [44], Gemini Code Assist [23], and Cursor [28] ask for user approval when writing a file or executing command-line commands.

中传统安全采用用户同意机制进行应用程序安装 [36] 和敏感数据访问 [9]。在智能体设置中，人在回路验证允许用户验证智能体行为和工具使用情况，从而为用户提供对安全决策的定制控制。人在回路验证可减少私有数据泄露 (R5)、意外操作和数据损坏 (R6) 以及资源消耗和拒绝服务 (R7)。这种防御对于智能体来说相对独特，因为智能体代表用户行事并与外部环境（例如文件、Web、第三方工具）交互，在高风险操作之前需要用户确认。代表作品。虽然致力于讨论智能体的人机循环验证的文献有限，但当代编码智能体（例如 GitHub Copilot [44]、Gemini Code Assist [23] 和 Cursor [28]）在编写文件或执行命令行命令时要求用户批准。

ENAgent defense systems [26, 29, 60, 144] often leverage human-in-the-loop validation when agents attempt actions that violate defense policies. These implementations demonstrate practical approaches to balancing automation with user oversight in sensitive contexts. Design Dimensions. Human-in-the-loop has the following design dimensions. • Validation scope: The scope of actions for which the agent requests user approval varies. Existing coding agents typically require approval for terminal commands, file accesses outside the current workspace, or destructive actions like file deletion.

中当智能体尝试采取违反防御策略的操作时，智能体防御系统 [26,29,60,144] 通常会利用人在回路验证。这些实现展示了在敏感环境中平衡自动化与用户监督的实用方法。设计尺寸。人机交互具有以下设计维度。• 验证范围：智能体请求用户批准的操作范围各不相同。现有的编码智能体通常需要批准终端命令、当前工作区之外的文件访问或文件删除等破坏性操作。

EN• User Alert: The content and format of alerts presented to users differ. Effective alerts should clearly explain the agent’s intended action, associated risks, and potential consequences to support informed decision-making. • Recurrence policy: Human-in-the-loop systems can implement mechanisms to remember and reuse previous user decisions for similar future requests, reducing prompt frequency while maintaining user control. Recent work [145] utilizes machine learning to model user preferences of permission approvals in tool-use agents and reduces the frequency of validation prompts by predicting user decisions. Limitations and Open Challenges.

中• 用户警报：向用户呈现的警报的内容和格式有所不同。有效的警报应清楚地解释智能体的预期行动、相关风险和潜在后果，以支持明智的决策。• 重复策略：人机交互系统可以实施机制来记住并重用以前的用户决策以应对类似的未来请求，从而在保持用户控制的同时降低提示频率。“允许一次”、“永不允许”和“始终允许”等选项反映了移动权限 [36]。最近的工作[145]利用机器学习对工具使用智能体中的权限批准的用户偏好进行建模，并通过预测用户决策来减少验证提示的频率。局限性和开放挑战。

ENFrequent validation prompts can overwhelm users and cause decision fatigue that undermines the intended safety benefits. Current alert mechanisms often assume a level of security literacy that many users do not possess, causing them to either blindly approve risky actions or overreact to benign ones. Practical systems require principled criteria for when to defer to human judgment, along with informative yet lightweight explanations that keep users engaged without overburdening them.

中频繁的验证提示可能会让用户不知所措，并导致决策疲劳，从而损害预期的安全效益。当前的警报机制通常假定许多用户不具备一定的安全素养水平，导致他们要么盲目批准有风险的行为，要么对良性行为反应过度。实用的系统需要关于何时遵循人类判断的原则性标准，以及信息丰富但轻量级的解释，以保持用户的参与而不给他们带来过重的负担。

【精读笔记】高风险确认应说明动作、工具、数据、目标、理由和最坏后果；单独弹出“是否允许”通常不足以支持知情判断。

5.3 安全内生设计 / Secure By Design

ENSecure-by-design defenses establish security properties at the architectural level, making agents intrinsically secure through fundamental design principles. As secure-by-design mechanisms depend on a system’s architecture and agents differ fundamentally from traditional systems, these defenses are naturally unique to agentic systems.

中设计安全防御在架构级别建立安全属性，通过基本设计原则使智能体具有本质安全性。由于设计安全机制取决于系统的架构，并且智能体与传统系统有根本不同，因此这些防御措施自然是智能体系统所独有的。

【补充笔记】安全内生设计假设模型终会犯错或受骗，并在架构上限制错误传播。它比事后检测更接近确定性控制，重点是划分信任域、权限域和执行环境。

5.3.1 权限分离 / Privilege Separation

ENFollowing the principle of least privilege, traditional security enforces privilege separation by assigning different privilege levels to different software components, exemplified by earlier automation attempts [14]. In agents, this concept extends to assigning privileges to different components and isolating these components to minimize the overall risk to the system. Privilege separation mitigates wrong instruction following (R2) by isolating untrusted data from decision-making components, and unconstrained data flow (R3) by enforcing boundaries between components with different trust levels. Representative Works. AirGap [11] separates the execution of LLM by first retaining only task-relevant data in memory, then performing the task with this minimized memory to prevent exposure of sensitive data. f-secure LLM [142], Camel [29], and FIDES [26] separate LLM operations into tool call planning and tool result parsing components.

中遵循最小权限原则，传统安全性通过向不同的软件组件分配不同的权限级别来强制执行权限分离，早期的自动化尝试就是例证[14]。在智能体中，这个概念扩展到向不同组件分配权限并隔离这些组件以最小化系统的总体风险。权限分离通过将不受信任的数据与决策组件隔离来减少错误指令遵循 (R2)，并通过在不同信任级别的组件之间强制执行边界来减少不受约束的数据流 (R3)。代表作品。AirGap [11] 通过首先在内存中仅保留与任务相关的数据来分离 LLM 的执行，然后使用最小化的内存执行任务以防止敏感数据泄露。 f-secure LLM [142]、Camel [29] 和 FIDES [26] 将 LLM 操作分为工具调用规划和工具结果解析组件。

ENBy avoiding direct feeding of tool results into planning, these systems prevent external data from controlling agent decisions. PFI [60] separates tools and environments into normal and sandbox versions, switching execution privilege based on the level of data trust. IsolateGPT [144] implements perapplication privilege separation for mobile systems, spawning dedicated agents that interact only with application-specific tools and resources to prevent cross-application exploitation. Design Dimensions. Privilege separation designs vary by separation policy and component scope. • Privilege Separation Policy: Vertical privilege separation implements hierarchical privileges, similar to kernel-user separation.

中通过避免将工具结果直接输入到规划中，这些系统可以防止外部数据控制智能体决策。PFI [60]将工具和环境分为普通版本和沙箱版本，根据数据信任级别切换执行权限。IsolateGPT [144] 为移动系统实现了每个应用程序的权限分离，产生了仅与特定于应用程序的工具和资源交互的专用智能体，以防止跨应用程序利用。设计尺寸。权限分离设计因分离策略和组件范围而异。• 权限分离策略：垂直权限分离实现分层权限，类似于内核-用户分离。

ENNotably, planner-parser separation [26,29,60,141,142] isolates tool call planning from tool result parsing. Horizontal privilege separation implements parallel sub-agents operating at disjoint access scopes. For instance, IsolateGPT [144] create perapplication agents that interact only with application-specific tools and resources. • Scope: Privilege separation techniques vary depending on the specific components being separated. LLM can be separated into planning and parsing processes [26, 29, 60, 142], preventing tool results from directly influencing planning decisions. Memory separation [11] creates separate memory spaces, protecting sensitive data from lower-privilege components.

中值得注意的是，规划器-解析器分离[26,29,60,141,142]将工具调用规划与工具结果解析隔离开来。水平权限分离实现了在不相交访问范围内运行的并行子智能体。例如，IsolateGPT [144] 创建仅与特定于应用程序的工具和资源交互的每个应用程序智能体。• 范围：权限分离技术根据要分离的特定组件而有所不同。LLM可以分为规划和解析过程[26,29,60,142]，防止工具结果直接影响规划决策。内存分离[11]创建单独的内存空间，保护敏感数据免受低权限组件的侵害。

ENExternal environment can leverage existing sandboxing mechanisms, such as containerization techniques in computer systems [76 –78] and fine-grained access control in web services [47,125]. Limitations and Open Challenges. Current privilege separation research primarily addresses generic indirect prompt injection in simplified environments [30]. It often fails to address real-world environment risks that present diverse and complex challenges requiring specialized separation strategies, such as web, file systems, and databases. Privilege separation entails utility loss by splitting functionality across isolated components. Dividing an agent into an effective set of least-privilege components remains an open challenge. Designing efficient communication across isolated components to reduce utility loss while maintaining security guarantees presents ongoing challenges for practical deployment.

中外部环境可以利用现有的沙箱机制，例如计算机系统中的容器化技术[76-78]和Web服务中的细粒度访问控制[47,125]。局限性和开放挑战。当前的权限分离研究主要解决简化环境中的通用间接提示注入[30]。它通常无法解决现实世界的环境风险，这些风险提出了多样化和复杂的挑战，需要专门的分离策略，例如网络、文件系统和数据库。权限分离会因将功能分散到孤立的组件而导致效用损失。将智能体划分为一组有效的最小权限组件仍然是一个公开的挑战。设计跨隔离组件的高效通信以减少效用损失，同时保持安全保证，这对实际部署提出了持续的挑战。

【精读笔记】不要让同一个 LLM 同时读取不可信数据、接触秘密、决定行动并执行高权限工具；被污染的组件应只能影响有限范围。

【补充笔记】权限分离的核心是让受污染组件只能影响有限范围。不要让同一个 LLM 同时读取不可信内容、接触秘密、决定行动并执行高权限工具；可拆分规划/解析、记忆区和执行沙箱。

5.3.2 形式化验证与可证明安全 / Provable Security with Formal Verification

ENTraditional security employs formal verification to provide theoretical proof of correctness and security [50, 62]. In agentic systems, formal verification approaches develop formal models of stochastic agent behavior and define verifiable properties within dynamic usage contexts. Representative Works. Formal verification for agents remains a new area with very limited existing work. VeriSafe Agent represents one of the few established approaches, developing formal specifications for mobile GUI agents and verifying behavioral alignment with initial user intentions [67]. Design Dimensions.

中传统安全采用形式验证来提供正确性和安全性的理论证明[50, 62]。在智能体系统中，形式验证方法开发随机智能体行为的形式模型，并在动态使用上下文中定义可验证的属性。代表作品。对智能体的形式验证仍然是一个新领域，现有工作非常有限。VeriSafe Agent 代表了少数已建立的方法之一，为移动 GUI 智能体开发正式规范并验证行为与初始用户意图的一致性 [67]。设计尺寸。

ENFormal verification approaches vary across formalization target and security property. • Formalization Target:VeriSafe Agent [67] formalizes user intent into a DSL over UI state transitions, verifying that proposed GUI actions align with the user’s task before execution. Formal-LLM [75] encodes developer-defined plan constraints (e.g., required tool orderings) as pushdown automata to restrict plan generation, ensuring validity and executability. ShieldAgent [20] structures external policy documents (e.g., regulations or corporate rules) into declarative rule circuits over action trajectories to enforce policy compliance and safety. • Security Property: Contextual security [67] ensures agents remain aligned with user intent and system policies. Safety property verification [20] guarantees agent actions do not violate predefined safety constraints or cause harmful outcomes.

中形式化验证方法因形式化目标和安全属性而异。• 形式化目标：VeriSafe Agent [67] 将用户意图形式化为 UI 状态转换上的 DSL，在执行之前验证建议的 GUI 操作是否与用户的任务一致。Formal-LLM [75] 将开发人员定义的计划约束（例如，所需的工具排序）编码为下推自动机，以限制计划生成，确保有效性和可执行性。ShieldAgent [20] 将外部策略文档（例如法规或公司规则）构建为行动轨迹上的声明性规则电路，以强制执行策略合规性和安全性。• 安全属性：上下文安全[67]确保智能体与用户意图和系统策略保持一致。安全属性验证[20]保证智能体行为不会违反预定义的安全约束或导致有害结果。

ENCorrectness property verification [75] ensures agent behavior conforms to specified functional requirements and produces expected outputs. Limitations and Open Challenges. Traditional formal methods are designed for programs written in code with structured language, while LLM-based agents operate based on probabilistic models. This fundamental difference creates challenges in developing formal models that capture the stochastic behavior of agents while preserving meaningful security guarantees. Moreover, security properties of agents that interact with various environment, such as web, file systems, or mobile applications, remain underspecified. Developing formal verification frameworks capable of addressing the full spectrum of agent security requirements largely remains an open challenge.

中正确性属性验证[75]确保智能体行为符合指定的功能要求并产生预期的输出。局限性和开放挑战。传统的形式化方法是为用结构化语言编写的程序而设计的，而基于 LLM 的智能体则基于概率模型进行操作。这种根本性的差异给开发正式模型带来了挑战，这些模型可以捕获智能体的随机行为，同时保留有意义的安全保证。此外，与各种环境（例如网络、文件系统或移动应用程序）交互的智能体的安全属性仍然没有明确规定。开发能够满足全方位智能体安全要求的正式验证框架在很大程度上仍然是一个开放的挑战。

【补充笔记】形式化验证尝试把用户意图和安全策略变成执行前可检查的规则。难点在于自然语言意图模糊、LLM 行为随机、环境开放且动态，因此更适合验证关键步骤和局部不变量。

5.4 身份与访问管理 / Identity and Access Management

ENIdentity and Access Management (IAM) encompasses identity management, access control, and credential management to ensure authenticated entity and authorized resource access. Traditional systems employ well-established IAM frameworks such as role-based access control (RBAC) [113] and OAuth-based delegation [37, 53], operating with static user identities and predefined permission boundaries. Agentic systems interacts with real-world services on behalf of users, thus require agent-specific identities, delegation mechanisms, and dynamic access control policies that adapt to runtime contexts.

中身份和访问管理 (IAM) 包括身份管理、访问控制和凭证管理，以确保经过身份验证的实体和授权的资源访问。传统系统采用完善的 IAM 框架，例如基于角色的访问控制 (RBAC) [113] 和基于 OAuth 的委派 [37, 53]，使用静态用户身份和预定义的权限边界进行操作。智能体系统代表用户与现实世界的服务交互，因此需要智能体特定的身份、委托机制和适应运行时上下文的动态访问控制策略。

【补充笔记】身份与访问管理回答三个问题：谁在行动、代表谁行动、可以访问什么。Agent、用户、任务和子 Agent 应具有可区分、可审计和可撤销的身份与授权。

5.4.1 身份管理 / Identity Management

ENIdentity management ensures that each actor operates under the correct identity with user authentication and authorization. In agent systems, identity management enables fine-grained control over agent behavior by defining agent identities and access scopes. It should support delegation, auditability, and regulatory accountability, while aligning with existing standards [37, 53, 133]. Identity management mitigates risks regarding illegal access (R5-R7) by ensuring proper authentication and authorization of agent operations. Representative Works. While there has been limited work in this area, existing solutions provide foundational approaches.

中身份管理通过用户身份验证和授权确保每个参与者以正确的身份进行操作。在智能体系统中，身份管理通过定义智能体身份和访问范围来实现对智能体行为的细粒度控制。它应该支持授权、可审计性和监管问责制，同时与现有标准保持一致[37,53,133]。身份管理通过确保智能体操作的正确身份验证和授权来降低非法访问 (R5-R7) 的风险。代表作品。尽管该领域的工作有限，但现有解决方案提供了基础方法。

ENOkta [97] and Composio [24] offers a single-sign-on (SSO) solution for agent access management, providing unified authentication and authorization across multiple agent services. Design Dimensions. Identity management varies by architecture, scope, and delegation model. • Architecture: Identity management can be centralized or decentralized. Centralized systems rely on identity providers running on OpenID Connect [37], while decentralized designs use distributed verification protocols [86] with greater autonomy and resilience. • Scope: Identity can be defined at user-level, agent-level, or task-level, each providing different granularity and accountability.

中Okta [97] 和 Composio [24] 为智能体访问管理提供单点登录 (SSO) 解决方案，跨多个智能体服务提供统一的身份验证和授权。设计尺寸。身份管理因架构、范围和委托模型而异。• 架构：身份管理可以是集中式的，也可以是分散式的。集中式系统依赖于在 OpenID Connect [37] 上运行的身份提供商，而去中心化设计则使用具有更大自主性和弹性的分布式验证协议 [86]。• 范围：可以在用户级别、智能体级别或任务级别定义身份，每个级别提供不同的粒度和责任。

ENUser-level identity ties actions directly to a human user, agent-level identity assigns distinct identities to individual agents, and task-level identity creates short-lived identities for specific tasks or sessions to support dynamic, least-privilege operation. • Delegation Model: Delegation governs how authority flows from users to agents. Direct delegation grants specific user permissions to agents, proxy delegation uses intermediary service or tokens to let agent act on behalf of users, and temporary delegation provides time-limited access that automatically expires to limit risk. Limitations and Open Challenges. Foundational questions persist about whether agent actions should be attributed to the human operator, the agent instance, or the task, and the answer often varies across domains.

中用户级身份将操作直接与人类用户联系起来，智能体级身份为各个智能体分配不同的身份，任务级身份为特定任务或会话创建短期身份，以支持动态、最低权限的操作。• 委派模型：委派控制权限如何从用户流向智能体。直接委派向智能体授予特定的用户权限，智能体委派使用中介服务或令牌让智能体代表用户行事，临时委派提供有时限的访问权限，该访问权限会自动过期以限制风险。局限性和开放挑战。关于智能体操作是否应归因于人类操作员、智能体实例或任务的基本问题仍然存在，并且答案通常因领域而异。

ENWithout standard frameworks, platforms implement incompatible credential issuance, delegation, and revocation flows that are hard to audit or federate. Robust identity management will require interoperable taxonomies and lifecycle tooling that preserve accountability while supporting seamless agent collaboration.

中如果没有标准框架，平台会实施不兼容的凭证颁发、委托和撤销流程，这些流程难以审计或联合。强大的身份管理将需要可互操作的分类法和生命周期工具，以在支持无缝智能体协作的同时保留责任。

【补充笔记】身份至少应区分用户、Agent 实例、单次任务和其他 Agent。清晰身份是权限检查、责任归属、跨 Agent 委托和事后审计的前提。

5.4.2 访问控制 / Access Control

ENIn agentic systems, access control can be enforced over internal memory and external environments, such as vector databases, file systems, and cloud drives. Paired with identity management (§5.4.1), access control prevents unauthorized accesses (R5-R7) by limiting an agent access to the permitted resources and operations. Representative Works. Bedrock [3] queries databases and filters results based on agent access permissions, providing role-based access control for RAG-based agent systems. Honeybee [157] proposes dynamic partitioning of vector databases to balance space-time trade-offs in access control, enabling efficient privilege enforcement for large-scale data retrieval. ControlNet [149] leverages internal neuron activations to enforce access control in vector databases, providing fine-grained permission management.

中在智能体系统中，可以对内部存储器和外部环境（例如矢量数据库、文件系统和云驱动器）实施访问控制。与身份管理（§5.4.1）配合使用，访问控制通过限制智能体对允许的资源和操作的访问来防止未经授权的访问（R5-R7）。代表作品。Bedrock [3] 查询数据库并根据智能体访问权限过滤结果，为基于 RAG 的智能体系统提供基于角色的访问控制。Honeybee [157] 提出矢量数据库的动态分区，以平衡访问控制中的时空权衡，从而为大规模数据检索提供有效的特权执行。ControlNet [149] 利用内部神经元激活来强制矢量数据库中的访问控制，提供细粒度的权限管理。

ENDesign Dimensions. Access control designs can have different mechanisms, policies, and scope of the resource. • Mechanism: Access control mechanisms determine how permissions are enforced, such as role-based access control (RBAC), attribute-based access control (ABAC), and capability-based security systems. • Policy: Access control policies define when access is granted, ranging from static permission rules to dynamic policies that adapt to changing contexts, user tasks, and environmental state. • Resource Scope: Access control can target different resource types including agent internal memory, external databases, tool APIs, and file systems. Limitations and Open Challenges.

中设计尺寸。访问控制设计可以具有不同的机制、策略和资源范围。• 机制：访问控制机制决定如何强制执行权限，例如基于角色的访问控制(RBAC)、基于属性的访问控制(ABAC) 和基于功能的安全系统。• 策略：访问控制策略定义何时授予访问权限，范围从静态权限规则到适应不断变化的上下文、用户任务和环境状态的动态策略。• 资源范围：访问控制可以针对不同的资源类型，包括智能体内存、外部数据库、工具API 和文件系统。局限性和开放挑战。

ENExisting access control work primarily targets retrieval-augmented LLM applications with vector databases [3,149,157], but agentic systems require broader coverage of diverse tools, data sources, and interagent interactions. Current deployments lack adaptive policy frameworks that can dynamically adjust to evolving tasks and trust contexts, instead relying on ad hoc, non-uniform policies that create mismatches across agents and gaps when coordinating with non-agentic services [111]. Usability challenges further exacerbate the problem, as configuration complexity leads to misconfigurations and excessive privileges even for technical users.

中现有的访问控制工作主要针对带有向量数据库的检索增强LLM应用程序[3,149,157]，但智能体系统需要更广泛地覆盖不同的工具、数据源和智能体间交互。当前的部署缺乏能够动态调整以适应不断变化的任务和信任上下文的自适应策略框架，而是依赖临时的、非统一的策略，这些策略在与非智能体服务协调时会在智能体之间造成不匹配和差距[111]。可用性挑战进一步加剧了问题，因为配置复杂性会导致错误配置和过多的特权，甚至对于技术用户也是如此。

【补充笔记】RBAC、ABAC 和能力令牌都可用于 Agent，但授权应随任务与上下文动态收缩。访问控制要落实到文件、记忆、向量库、工具 API、云服务和 Agent 通信，而不只保护登录入口。

5.4.3 凭证管理 / Credential Management

ENAI agents must manage diverse credential types to interact with external services and access user resources. These include tool API credentials (e.g., API keys and access tokens for third-party services) and environmental credentials (e.g., one-time passwords from email, session tokens). The agent’s exposure to these sensitive credentials raises significant privacy and security concerns [94, 129], necessitating robust credential and secret management practices. Credential management primarily mitigates private data leakage (R5) by securely storing and handling sensitive credentials. Representative Works. OpenAI’s temporary chat feature [103] allows users to prevent chat history storage and model training usage, protecting agent memory credentials.

中AI 智能体必须管理不同的凭证类型才能与外部服务交互并访问用户资源。其中包括工具 API 凭证（例如，第三方服务的 API 密钥和访问令牌）和环境凭证（例如，电子邮件中的一次性密码、会话令牌）。智能体接触这些敏感凭证会引起严重的隐私和安全问题 [94, 129]，因此需要强大的凭证和秘密管理实践。凭证管理主要通过安全地存储和处理敏感凭证来减少私人数据泄漏 (R5)。代表作品。OpenAI 的临时聊天功能 [103] 允许用户阻止聊天历史记录存储和模型训练使用，从而保护智能体内存凭证。

ENComposio [24] offers credential management using singlesign-on (SSO) to securely manage API keys and access tokens, mitigating tool credential leakage. Authenticated delegation mechanisms [126] based on OAuth 2.0 provide a secure transfer of credentials from users to agents. Design Dimensions. Credential management approaches span different ways of storing confidential data and managing their lifecycle. • Confidential Storage: Secure storage of agent credentials can be implemented through multiple approaches with different security guarantees. Encrypted storage protects credentials at rest using encryption techniques, preventing unauthorized access even if the storage media is compromised.

中Composio [24] 使用单点登录 (SSO) 提供凭证管理，以安全地管理 API 密钥和访问令牌，从而减少工具凭证泄漏。基于 OAuth 2.0 的经过身份验证的委托机制 [126] 提供从用户到智能体的安全凭证传输。设计尺寸。凭证管理方法涵盖存储机密数据和管理其生命周期的不同方式。• 机密存储：智能体凭证的安全存储可以通过具有不同安全保证的多种方法来实现。加密存储使用加密技术保护静态凭据，即使存储介质受到损害，也可以防止未经授权的访问。

ENTemporary storage minimizes exposure by maintaining credentials only for the duration of active sessions, exemplified by OpenAI’s temporary chat feature [103] that prevents chat history storage and model training usage. Confidential computing techniques can be leveraged to securely manage credentials within hardware-based trusted execution environments [64, 118]. • Credential Lifecycle Management:Credential management systems face choices in how to handle credential lifecycles and access patterns. Static credential management maintains persistent credentials throughout agent sessions, providing convenience and consistent access, but increasing exposure risk over time. Dynamic credential management uses time-limited tokens that automatically expire, reducing exposure windows but requiring more complex renewal mechanisms and potential service interruptions.

中临时存储通过仅在活动会话期间维护凭证来最大程度地减少暴露，OpenAI 的临时聊天功能 [103] 就是一个例子，它可以防止聊天历史记录存储和模型训练使用。可以利用机密计算技术来安全地管理基于硬件的可信执行环境中的凭证[64, 118]。• 凭证生命周期管理：凭证管理系统面临如何处理凭证生命周期和访问模式的选择。静态凭证管理在整个智能体会话期间维护持久凭证，提供便利和一致的访问，但随着时间的推移会增加暴露风险。动态凭证管理使用有时限的令牌，这些令牌会自动过期，从而减少暴露窗口，但需要更复杂的更新机制和潜在的服务中断。

EN• Confidential storage: Credentials are protected through various storage mechanisms, including encryption at rest, temporary storage that persists only for active sessions [103], or hardware-based trusted execution environments [64, 118]. • Lifecycle management: Credential lifecycle management determine how credentials are maintained over time, ranging from static credentials that persist throughout agent sessions to dynamic time-limited tokens that automatically expire, reducing exposure windows. • Credential provisioning: Credential provisioning determines how agents obtain credentials, including singlesign-on (SSO) mechanisms [24] and authenticated delegation based on OAuth 2.0 [126] for secure credential transfer from users to agents. Limitations and Open Challenges. Agent stacks still rely on ad-hoc secret handling, lacking standardized practices for credential protection.

中• 机密存储：凭证通过各种存储机制受到保护，包括静态加密、仅针对活动会话持续的临时存储[103]或基于硬件的可信执行环境[64, 118]。• 生命周期管理：凭证生命周期管理决定如何随着时间的推移维护凭证，范围从在整个智能体会话期间持续存在的静态凭证到自动过期的动态限时令牌，从而减少暴露窗口。• 凭证配置：凭证配置决定智能体如何获取凭证，包括单点登录(SSO) 机制[24] 和基于OAuth 2.0 [126] 的身份验证委派，以实现从用户到智能体的安全凭证传输。局限性和开放挑战。智能体堆栈仍然依赖于临时秘密处理，缺乏凭证保护的标准化实践。

ENMany frameworks guide developers to store internal credentials, such as API keys, as unencrypted environment variables, increasing the risk of leakage. Multiagent systems further complicate secret sharing, making it difficult to maintain least privilege and traceability, and underscoring the need for coordinated credential orchestration.

中许多框架引导开发人员将内部凭据（例如 API 密钥）存储为未加密的环境变量，从而增加了泄露的风险。多智能体系统进一步使秘密共享变得复杂，使得维护最小权限和可追溯性变得困难，并强调了协调凭证编排的必要性。

【精读笔记】API Key、OAuth Token、会话令牌和一次性密码不应直接暴露在模型上下文中，应优先采用受控凭证代理和短期可撤销授权。

【补充笔记】API Key、OAuth Token 和会话令牌不应直接暴露在模型上下文中。优先使用受控凭据代理、短期任务凭据、自动过期与可撤销授权，缩小泄露后的时间和权限范围。

5.5 组件加固 / Component Hardening

ENComponent hardening strengthens individual agent components including LLMs and third-party tools against their specific vulnerabilities, recognizing that agents are only as secure as their weakest component. Model Hardening. Model hardening mitigates model-level risks such as wrong instruction following (R2) and hallucination (R4) by improving model robustness and reliability. SecAlign [18] and StruQ [17] fine-tune models to consistently follow initial instructions even when faced with conflicting directives, mitigating wrong instruction following. Instruction hierarchy-aware model training [134, 143] ensures system prompts maintain priority over user input and external data. Tool Hardening.

中组件强化增强了各个智能体组件（包括LLM和第三方工具）针对其特定漏洞的能力，并认识到智能体的安全性取决于其最薄弱的组件。模型强化。模型强化通过提高模型的稳健性和可靠性来减轻模型级风险，例如错误指令遵循 (R2) 和幻觉 (R4)。SecAlign [18] 和 StruQ [17] 微调模型，即使面临指令冲突，也能始终遵循初始指令，从而减少错误的指令遵循。指令层次结构感知模型训练 [134, 143] 确保系统提示保持高于用户输入和外部数据的优先级。工具硬化。

ENTool hardening mitigates heterogeneous untrusted interfaces (R1) by ensuring tool integrity, verifying tool descriptions, and preventing tool supply chain attacks through systematic auditing. Extended Tool Definition Interface (ETDI) [33] implements cryptographically signed and versioned tool control, ensuring integrity throughout the tool lifecycle to prevent tool poisoning. Anthropic’s Connectors Directory [7] maintains a curated repository of trusted tools with reviewed descriptions, functionality, and safety policies. MCP Context Protector [131] creates an MCP proxy that enforces manual review processes and applies guardrail checks to prevent tool poisoning attacks. MCP Safety Audit [109] introduces systematic protocols to examine agent tools, identifying potentially exploitable behaviors from malicious logic or misleading descriptions. MCIP [59] enhances MCP with observability and an LLM fine-tuned to detect threats in MCP usage.

中工具强化通过确保工具完整性、验证工具描述以及通过系统审计防止工具供应链攻击来缓解异构不可信接口 (R1)。扩展工具定义接口（ETDI）[33]实现了加密签名和版本控制的工具控制，确保整个工具生命周期的完整性，以防止工具投毒。Anthropic 的连接器目录 [7] 维护着一个受信任工具的精选仓库，其中包含经过审查的描述、功能和安全策略。MCP Context Protector [131] 创建一个 MCP 智能体，强制执行手动审查流程并应用防护检查以防止工具投毒攻击。MCP 安全审计 [109] 引入了系统协议来检查智能体工具，从恶意逻辑或误导性描述中识别潜在的可利用行为。MCIP [59] 增强了 MCP 的可观察性，并且 LLM 经过微调以检测 MCP 使用中的威胁。

ENLimitations and Open Challenges. Current component hardening approaches focus on simplified threat scenarios that do not reflect the complexity of real-world agent systems. Model hardening techniques like instruction hierarchy fine-tuning primarily address simple scenarios involving system prompts, user prompts, and tool results, failing to address sophisticated attacks such as shadowing attacks, where malicious tool results override other tool results. The role of each component and appropriate threat models for comprehensive hardening remain unclear.

中局限性和开放挑战。当前的组件强化方法侧重于简化的威胁场景，无法反映现实世界智能体系统的复杂性。指令层次微调等模型强化技术主要解决涉及系统提示、用户提示和工具结果的简单场景，无法解决诸如影子攻击之类的复杂攻击，其中恶意工具结果会覆盖其他工具结果。每个组件的作用以及用于全面强化的适当威胁模型仍不清楚。

【精读笔记】MCP 安全属于 Agent 的工具、接口和供应链安全，只是 Agent 安全的一部分。

【补充笔记】组件加固包括模型的指令层级训练，也包括工具与 MCP 的签名、版本管理、可信目录、安全审计和调用监控。MCP 安全属于工具与供应链安全的一部分，不等于全部 Agent 安全。

5.6 防御设计原则 / Defense Design Principles

ENEffective agent security requires multiple complementary defense mechanisms working together rather than relying on any single approach. Three fundamental security principles guide effective agent defense design. We note that additional principles can also be applied to agents (e.g., fail-safe defaults and economy of mechanisms). Defense-in-Depth. Defense mechanisms complement each other by operating at different stages and targeting different attack vectors. Input guardrails (§5.2.1) provide first-line protection by filtering malicious inputs, while output guardrails (§5.2.2) serve as last-line defense by sanitizing agent outputs. Information flow control (§5.2.3) and monitoring (§5.2.4) provide continuous runtime protection throughout agent execution, while access control (§5.4.2) ensures proper authentication and authorization Secure-by-design approaches like privilege separation (§5.3.1) establish fundamental architectural protections. Component hardening (§5.5) strengthens individual elements, and human-in-the-loop validation (§5.2.5) provides user oversight for critical decisions. Principle of Least Privilege.

中有效的智能体安全需要多种互补的防御机制协同工作，而不是依赖任何单一方法。三个基本安全原则指导有效的智能体防御设计。我们注意到，其他原则也可以应用于智能体（例如，故障安全默认值和机制的经济性）。纵深防御。防御机制通过在不同阶段运行并针对不同的攻击向量来相互补充。输入护栏（§5.2.1）通过过滤恶意输入提供一线保护，而输出护栏（§5.2.2）通过净化智能体输出作为最后一道防御。信息流控制（第 5.2.3 节）和监控（第 5.2.4 节）在整个智能体执行过程中提供持续的运行时保护，而访问控制（第 5.4.2 节）可确保正确的身份验证和授权 权限分离（第 5.3.1 节）等安全设计方法建立了基本的体系结构保护。组件强化（第 5.5 节）可强化各个元素，而人在回路验证（第 5.2.5 节）则为关键决策提供用户监督。最小权限原则。

ENAgents should operate with minimal necessary permissions and access rights. This principle is implemented through privilege separation techniques (§5.3.1) that isolate agent components and restrict tool access to only what is required for specific tasks. Complete Mediation. All access to sensitive resources should be checked and validated. This principle is reflected in comprehensive monitoring systems (§5.2.4) and access control mechanisms (§5.4.2) that verify every agent interaction with protected resources.

中智能体应以最低限度的必要权限和访问权限进行操作。这一原则是通过权限分离技术（第 5.3.1 节）来实现的，该技术隔离智能体组件并将工具访问限制为仅特定任务所需的内容。完全仲裁。应检查和验证对敏感资源的所有访问。这一原则反映在综合监控系统（第 5.2.4 节）和访问控制机制（第 5.4.2 节）中，用于验证每个智能体与受保护资源的交互。

【精读笔记】最小纵深防御链：输入检查 → 规划/输出检查 → 信息流控制 → 访问控制 → 沙箱与权限分离 → 运行监控 → 高风险动作人工确认。

【补充笔记】三项最终原则应同时使用：纵深防御组合多层控制；最小权限限制 Agent、工具和子 Agent；完全仲裁要求每次敏感资源访问都重新检查，而不是首次允许后永久信任。
